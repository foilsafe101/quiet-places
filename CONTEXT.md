# Shhh — Map of Quiet Places

A web map identifying locations on Earth with no audible anthropogenic sound. Mark Tribe (SVA faculty, NYC, field recordist) uses it to scout recording locations. Northeast US (Quebec, Labrador, Newfoundland, Nova Scotia) is his personal coverage priority.

## Architecture

### Data sources
- **Flight positions:** OpenSky Network Trino historical DB via `pyopensky.trino.Trino`. Authenticated as `mtribe@sva.edu`. Resource group: `global.readonly.mtribe@sva.edu`. Limited to 2 concurrent + 2 queued queries at the server.
- **Roads:** Natural Earth `ne_10m_roads.zip` (in `data/`)
- **Railroads:** Natural Earth `ne_10m_railroads.zip` (in `data/`)

### Key files
- `docs/index.html` — Leaflet frontend. Single canvas layer (`FlightCanvas`) renders all flight tracks in one stroke. Loads three gzipped JSON files in parallel: `flights.json.gz` (current single-worker output), `flights_0.json.gz`, `flights_1.json.gz` (legacy worker outputs).
- `docs/quiet_overlay.png` — Web Mercator RGBA overlay (1440×1019), dark blue = quiet. Generated by `generate_quiet_overlay.py`.
- `docs/flights.json.gz` — Current single-worker output (gzipped).
- `docs/flights_0.json.gz`, `docs/flights_1.json.gz` — Legacy outputs from when we ran two parallel workers. Still loaded by HTML for the historical 3-min-sampled tracks they contain.
- `query_opensky_paths.py` — OpenSky query script. Single-process when `--worker` omitted; honors `--worker N` for multi-process splits (no longer used after the May 2026 incident — see below).
- `generate_quiet_overlay.py` — Computes quiet zones via cKDTree distance from flight + road/rail samples. Outputs Web Mercator PNG (NOT equirectangular — was a bug fixed earlier).
- `run_worker.sh` — Single-process supervisor with PID-file lockout. Replaces the old `run_batches.sh` which left zombie bash loops across sessions.

### Region grid (30 uniform tiles)
30°×60° tiles, 5 lat bands × 6 lon columns, lat -60° to 90°, lon -180° to 180°. Defined in `query_opensky_paths.py:LAND_REGIONS`. Replaced the older 11 hand-drawn regions on 2026-05-03.

## Process management

**Always check at session start:** `pgrep -fl "run_worker|run_batches|query_opensky"`

The supervisor `run_worker.sh`:
- Single python process, no `--worker` flag
- Writes PID to `/tmp/shhh-worker.pid`
- Refuses to start if PID file exists with a live process
- Loops batch-of-200 forever, commits + pushes after each batch
- Trap removes PID file on exit (INT/TERM/EXIT)

To stop: `kill $(cat /tmp/shhh-worker.pid)`. To start: `cd /Users/Shared/shhh && nohup ./run_worker.sh >/dev/null 2>&1 & disown`.

## OpenSky / Martin Strohmeier incident (2026-05-04 to 05)

**Symptom:** Two emails from Martin (OpenSky support, hello@opensky-network.org) complaining about overlapping queries, including a screenshot showing QUERY_QUEUE_FULL errors.

**Root cause:** Previous Claude Code sessions had launched `run_batches.sh` in the background with `&`. Those bash loops survived across sessions and continued spawning Python workers indefinitely. A `pkill -f query_opensky` at session start only killed active children, not the parent bash supervisors. `ps auxww` revealed 6 zombie python processes + 6 zombie bash loops from prior days, all making concurrent queries.

**Fix:**
1. Killed all parent bash loops (`pkill -9 -f run_batches`) — the python children died with their parents
2. Replaced `run_batches.sh` with `run_worker.sh` using PID-file lockout
3. Single sequential process (no `--worker`)
4. Bumped `PAUSE_SECONDS` 3 → 30 (subsequently to 0 once Mark and I confirmed the only real issue had been overlap, not rate)

**Communication with Martin:**
- Mark sent one apology email (drafted via Gmail MCP, Mark hit send) acknowledging the issue and saying he'd reduce to single process with longer pause
- Martin replied still complaining → that turned out to be the zombie-process discovery
- After the proper fix, no further emails — Mark explicitly does NOT want to send more emails to Martin. Don't initiate further contact.

**Why PAUSE=0 is OK:** Other pyopensky users (e.g. `leek27@erau.edu`, visible in Trino UI) submit back-to-back queries with no pause and Martin doesn't email them. Our queries are short (2–5s each), single-threaded, and Trino's resource-group quota (2 concurrent + 2 queued) is the actual hard guardrail. Sequential queries cannot exceed 1 concurrent.

## Sampling-density tradeoff (decided 2026-05-05)

Considered intervals and effects on flight-path accuracy near turns:
| Interval | Distance between samples | Worst-case turn error |
|---|---|---|
| 3 min | 42 km | 10–15 km |
| 6 min | 84 km | 25–35 km |
| 9 min | 126 km | 40–55 km |
| 12 min | 168 km | 60–80 km |
| 15 min | 210 km | 70–90 km |

**Chose 12 min** because:
- ~2.5M legacy tracks already at 3-min sampling are preserved (loaded by HTML from `flights_0/1.json.gz`)
- New uniform-grid coverage fills oceans/remote regions where flights cruise straight (no turns to corner-cut)
- Airport terminal areas — where the corner-cut artifact would matter — are already saturated noisy in the existing data
- 12 is a multiple of 3, so existing 3-min progress at minutes 0, 12, 24, 36, 48 is preserved (~25% of completed slots, 41,602 of 166,350)

**Asymmetry to remember:** when a corner-cut path is wrong, it's wrong toward over-stating noise (drawing a line through points the plane didn't quite hit). The map is conservative against "false quiet."

## Known gotchas / lessons

1. **Zombie processes** — always `pgrep -fl` at session start. Bash supervisors started with `&` survive Claude Code session ends.
2. **Multiple progress files** — when migrating regions or sampling, old progress doesn't auto-merge. Manually consolidate.
3. **Data file flow mismatch** — single-worker writes to `docs/flights.json.gz`; HTML must explicitly load it. Legacy `_0`/`_1` files contain valuable 3-min-sampled data; don't delete.
4. **GitHub 100MB file limit** — uncompressed `flights*.json` files exceed it. We use gzip. Some uncompressed `.json` files in `docs/` are stale from before the gzip migration; they're not loaded by HTML and can be cleaned up if desired.
5. **Memory file claims may go stale** — verify with `git log --oneline -5`, `pgrep`, and progress-file inspection at session start.
